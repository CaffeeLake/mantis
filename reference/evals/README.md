# Mantis ADK Evaluation Harnesses

Benchmarks for the reference pipeline, cheapest first. Tier 1 costs zero tokens;
run it on every ranking change. Tier 2 costs one researcher campaign per
configuration; run it when researcher tooling, prompts, or models change.

## Tier intent

Each tier answers one question in isolation, and a pass at one tier does not
transfer upward: a ranking improvement (Tier 1) is not evidence of better
detection (Tier 2), and a single-stage win is not evidence of an end-to-end win.
Run the cheapest tier that can falsify the change being made.

The downstream stage benchmarks
(`run_eval.py --stage dedupe|review|critic|calibrate`) sit alongside Tier 2 at
the same cost scale: fixed datasets, one stage judged in isolation per dataset
row, so a regression is attributed to the stage that caused it rather than to
the pipeline as a whole.

There is deliberately no end-to-end tier yet. A full-pipeline score folds every
stage's variance into one number, which can say "worse" without saying where;
the stage benchmarks are that diagnostic layer. An end-to-end tier earns its
spend only once a corpus is large enough to separate real movement from
run-to-run noise, which the current seeded corpus is not.

## Tier 1 — Surveyor ranking benchmark (`surveyor_benchmark.py`)

Deterministic, no LLM. Scores the Phase-0 ranked map against known vulnerable
file locations: recall@k, nDCG@k, MRR, and a coverage ceiling that separates
"ranked late" from "never sliced".

```bash
# Hermetic self-check against the generated synthetic webapp:
python3 evals/surveyor_benchmark.py --synthetic

# External target with a curated ground truth (clone pinned to the release
# the ground truth was verified against -- see ground_truth/juice_shop.json):
git clone --depth 1 --branch v20.2.0 \
    https://github.com/juice-shop/juice-shop ~/src/juice-shop
python3 evals/surveyor_benchmark.py --target ~/src/juice-shop \
    --ground-truth evals/ground_truth/juice_shop.json

# Machine-readable output for before/after comparison:
python3 evals/surveyor_benchmark.py --synthetic --json-out /tmp/after.json
```

The synthetic target is generated by `synthetic_repo.py` (seeded vulnerable
files plus demoted decoys carrying the same sink patterns); its ranking
properties are pinned by `tests/test_surveyor_benchmark.py`.

Two caveats on the juice-shop ground truth:

- **Zero-LLM tier only.** Juice Shop's vulnerabilities are documented in public
  writeups, so an LLM-stage eval against it would be inflated by pretraining
  contamination. It is valid here only because the surveyor is deterministic
  code. Do not use publicly documented vulnerable apps as LLM-stage targets.
- **In-sample check, not external validity.** The surveyor's thresholds were
  calibrated on juice-shop measurements (see `core/surveyor.py`), so these
  scores are a regression check on the calibration corpus, not evidence of
  generalization. The ground truth pins the upstream commit it was verified
  against; running any other checkout is flagged in the report and in the JSON
  (`upstream_pin.commit_match`).

## Tier 2 — Researcher stage eval (`research_eval.py`)

Measures the stage that produces findings: detection recall, cross-file recall,
precision, and tokens per true finding over the seeded corpus in
`research_target/` (ground truth is excluded from the eval jail). The toolset is
the independent variable — `--toolset structural` adds the structural navigation
tools (`find_symbol`, `find_callers`, `find_callees`, `get_function_boundary`),
and the harness builds their tree-sitter catalog for the jail before the run.

`research_target/` is a deliberately vulnerable, never-executed corpus. Do not
"fix" its seeded flaws, and do not add comments that describe them: the files
are copied into the eval jail, so they must read like ordinary production code
or they leak the answers to the model under evaluation. Flaw documentation
belongs only in `research_target/ground_truth.json`.

```bash
# Model sweep with distribution over runs:
python3 evals/run_eval.py --stage research --runs 3

# Single configuration, explicit toolset A/B:
python3 evals/research_eval.py --model vertex_ai/gemini-3.8-flash \
    --effort low --toolset baseline --json-out /tmp/baseline.json

# Two arms at equal spend; the score is recall at the cap:
python3 evals/research_eval.py --toolset baseline   --max-tokens 1500000 ...
python3 evals/research_eval.py --toolset structural --max-tokens 1500000 ...
```

### What a result says about itself

Recall on a 26-file corpus says little about a repository that does not fit in
one context window, so every result also records *how* the run read, and whether
the number is a measurement at all:

- `telemetry`: whole-file vs windowed `read_file` calls (a read with
  `start_line=0, end_line=0` is whole-file), structural navigation calls,
  loop-guard hints fired, unique files read, repeated whole-file reads, and the
  cumulative token count at each `report_findings` call (the raw material for a
  recall-vs-tokens curve).
- `graded` / `status`: a run that crashed is `ungraded`. Its partial findings
  are kept for a human reader, but `run_eval.py` leaves it out of every mean and
  counts it as a failure — a crash is a missing measurement, not a low score. A
  run that completed and reported nothing is a real zero
  (`zero_findings_complete`).
- `cap_hit`: the run was stopped at `--max-tokens` / `--max-tool-calls`; still
  graded, as recall@cap.
- `config_fingerprint` / `ground_truth_version`: what was measured (model,
  effort, tools, prompt) and against which answer key. `run_eval.py` warns when
  runs that differ in either are averaged together. A toolset whose tools are
  not all registered fails to run rather than quietly becoming the other arm.

### Generated targets (`research_targets/gen.py`)

The hand-written corpus is one sample, and it fits in a context window. For any
claim that a change *improves* the researcher, use generated targets:

```bash
python3 evals/research_targets/gen.py --seed 1001 --size medium --out /tmp/t1001
python3 evals/research_eval.py --target /tmp/t1001 --toolset structural --max-tokens 1500000 ...
python3 evals/research_targets/gen.py --list dev        # 1000-1099
python3 evals/research_targets/gen.py --list holdout    # 9000-9099 (needs --allow-holdout to write)
```

- `generate(seed, size)` is deterministic. Each target carries ~11 **seeded**
  bugs across ten classes (most of them 2–3 hop route → service → store flows)
  and ~7 **decoys**: the same sink behind a real mitigation (`decoy_sanitized`),
  the same code with no caller (`decoy_dead`), and the same pattern under
  `tests/` or `vendor/` (`decoy_vendor`). A report that matches a decoy is
  scored as a certain false positive (`decoy_fp_rate`, `precision` strict vs
  `precision_lenient`).
- `--size small|medium|large` pads the tree with benign modules (≈70 / 220 / 700
  files) so that reading everything stops fitting in context — the condition
  under which navigation is supposed to matter.
- **Holdout is by construction.** Seeds 9000–9099 are for one-shot confirmation
  after a change passes on dev seeds; `assert_not_holdout` refuses to build a
  proposer, reflector, or tuning context on them, and one bug class (`xss`)
  never appears in dev targets. Burned holdout seeds should be retired to dev.
- The generated tree must read like ordinary code;
  `tests/test_research_targets.py` greps every file for words that would name a
  flaw.

### Sweeps and the change gate (`sweep.py`, `compare.py`)

A single comparison is a sample. `sweep.py` runs the matrix
`{arm × seed × repeat}` **interleaved in time** (both arms back to back per
target, so model drift hits them equally), writes one directory per cell, marks
a cell complete only after a graded return (re-rolling crashes up to
`--max-attempts`, then keeping the failure as `exhausted`), and locks the
directory to one identity (model, effort, arms, seeds, caps) so two different
measurements cannot share it. `compare.py` reads the cells and applies the gate
a change must clear:

```bash
python3 evals/sweep.py --out runs/dev-1 --arms baseline,structural --seeds dev:10 \
    --repeats 3 --size medium --max-tokens 1500000 --model vertex_ai/gemini-3.8-flash
python3 evals/compare.py runs/dev-1 --baseline baseline --candidate structural
# after it passes on dev, once:
python3 evals/sweep.py --out runs/holdout-1 --seeds holdout:8 --confirm-holdout ...
python3 evals/compare.py runs/holdout-1
```

The gate, over **targets** (repeats on one target are correlated through it):

1. paired-bootstrap 95% CI of Δrecall has lower bound > 0, **or** the CI
   contains 0 and tokens-per-true-finding improves ≥ 20% with its own CI
   excluding 0;
2. mean Δrecall exceeds **2× the baseline's A/A noise floor** (mean absolute
   difference between baseline repeats on the same target — the number a single
   run's "improvement" has to beat);
3. worst-target Δrecall ≥ −0.10;
4. decoy false-positive rate and the ungraded / zero-finding / re-armed rates do
   not increase.

It also reports **union gain** for two arms — union recall against the best
single arm and against what two independent samplers would reach — so a second
arm that merely re-samples the first is visible. Suggested sizes: smoke 10
targets × 1 repeat × 2 arms (20 campaigns); dev 10 × 3 × 2 (60); holdout 8 × 3 ×
2 (48), run once. Past ~30 targets, spend on targets rather than repeats.

### Field evidence: toolset A/B on an external target

The seeded corpus measures recall; it cannot say whether the structural toolset
finds bugs the baseline cannot. A two-round existence test (three runs per arm
per round, same model and prompt in both arms) against a widely shipped
~58k-line C driver subsystem — large enough that exhaustive reading does not fit
in a context window; the specific target is withheld until the findings are
verified fixed upstream — was scored by manually adjudicating every reported
finding against the pinned source instead of by recall.

Round-2 aggregates: baseline 2 real findings out of 9 reported (22% precision)
at 10.7M tokens; structural 3 real out of 4 reported (75% precision) at 5.0M
tokens. One real bug was found only by the structural arm, via a `find_callers`
hop onto a call site passing an undersized caller buffer into an unchecked copy;
zero of six baseline runs reported it although four had read the containing file
in full. One real bug was found only by the baseline (an overflow visible in a
single whole-file read), so the toolsets are complementary, not ordered. A
macro-related false positive (indexing deleted by preprocessing, zero callers)
was reported by every round-2 baseline run and by no run that actually used the
index.

Two operational caveats transfer to any rerun: models do not pick up the
structural tools unprompted, so the researcher prompt must direct them to prefer
function-level retrieval when the tools are present; and read-everything runs on
large targets can re-read large files until they exhaust the context window, so
cap tool calls or budget accordingly.

```bash
python3 evals/run_eval.py --stage all --runs 3
```
